#23 p404 a455
Q: How is search done in `#include <somelibrary.h>` and `#include "somelibrary.h"` according to C standard?
a) When former is used, current directory is searched and when latter is used, standard directory is searched
b) When former is used, standard directory is searched and when latter is used, current directory is searched
c) When former is used, search is done in implementation defined manner and when latter is used, current directory is searched
d) For both, search for 'somelibrary' is done in implementation-defined places
K: d
B: b
X: The C standard (§6.10.2) says both forms search implementation-defined places. The quoted form searches in an implementation-defined manner first and, if that fails, falls back to the `<>` search. #44 p408 a456
Q: What is the difference between the following 2 C codes?
```
#include <stdio.h> //Program 1
int main()
{
    int d, a = 1, b = 2;
    d = a++ + ++b;
    printf("%d %d %d", d, a, b);
}

#include <stdio.h> //Program 2
int main()
{
    int d, a = 1, b = 2;
    d = a++ +++b;
    printf("%d %d %d", d, a, b);
}
```
a) No difference as space doesn't make any difference, values of a, b, d are same in both the case
b) Space does make a difference, values of a, b, d are different
c) Program 1 has syntax error, program 2 is not
d) Program 2 has syntax error, program 1 is not
K: d
X: The compiler reads the longest possible token each time (maximal munch). So `a++ +++b` is split as `a++ ++ +b`, which applies `++` to the non-lvalue `a++` and is a compile error. Program 1 is fine: d = 1 + 3 = 4, a = 2, b = 3.
S: Maximal munch: +++ → ++ then +.

#48 p409 a457
Q: What will be the final values of i and j in the following C code?
```
#include <stdio.h>
int x = 0;
int f()
{
    if (x == 0)
        return x + 1;
    else
        return x - 1;
}
int g()
{
    return x++;
}
int main()
{
    int i = (f() + g()) | g(); //bitwise or
    int j = g() | (f() + g()); //bitwise or
}
```
a) i value is 1 and j value is 1
b) i value is 0 and j value is 0
c) i value is 1 and j value is undefined
d) i and j value are undefined
K: d
B: c
X: The operands of `+` and bitwise `|` may be evaluated in any order, and f() and g() read and change the global x. For i, calling f, then the outer g, then the inner g gives (1 + 1) | 0 = 2, while left-to-right gives 1. So even i is not fixed, and j depends on the state left by i's calls. (GCC happens to give i = 1, j = 7.) With logical `||`, which is evaluated left to right with short-circuiting, the result would be defined.
S: Bitwise | / + : operand order unspecified → side effects unpredictable.
N: The book prints (c), claiming i is certainly 1. Trying the possible call orders shows i can also be 2, so neither value is fixed by the language. The key is (d).

b) An exception that must be explicitly caught or declared
c) An exception related to hardware failures
d) An exception that is automatically handled
K: b
X: A checked exception (e.g. IOException) must be caught or declared with `throws`, and the compiler enforces this. Unchecked exceptions (RuntimeException subclasses such as NullPointerException) need not be.

Q: Which of the following is NOT a common category of exceptions?
a) Arithmetic exceptions
b) Logic exceptions
c) Input/output exceptions
d) Null pointer exceptions
K: b
X: Arithmetic (divide by zero), I/O (file not found) and null-pointer exceptions are standard run-time exception categories, e.g. Java's ArithmeticException, IOException and NullPointerException. Logic errors are bugs in reasoning, usually not raised as exceptions. (C++ does have a `std::logic_error` class, but (b) is the intended answer.)
S: Logic error = wrong result, not an exception.

Q: What is the term for preventing exceptions by checking for potential issues in advance?
a) Exception handling
b) Error propagation
c) Exception prevention
d) Defensive programming
K: d
X: Defensive programming checks inputs and conditions before acting (e.g. testing a divisor for zero or a pointer for NULL), so that errors are prevented rather than handled after they occur.
S: Check first → defensive programming.
